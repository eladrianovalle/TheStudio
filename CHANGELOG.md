# Changelog

All notable changes to TheGameStudio are documented here.

---

## [Unreleased]

### Added
- The evidence skeleton `/spec` prints now warns about void arms before you trust either row of the table. Proving `find-before-you-grep` took six runs to get one valid comparison, and both failures were instrument errors rather than anything about the feature: a baseline is only a baseline if the behaviour under test cannot reach the agent by another route (a skill, a hook, an MCP server, CLAUDE.md), and a treatment is only a treatment if the file carrying it actually loads. Every future prompt-shaped feature inherits the warning instead of rediscovering it.
- The `/forge` static check runs the lint command your repo actually uses, instead of a tool name the loop guessed at. `static_checks` in `implementation_loop.toml` now holds **commands** — `ruff check {paths}` for Python, `npm run lint` or `npx eslint {paths}` for Node — and `{paths}` is replaced with the files the unit touched. A config file still carrying a bare `ruff`, `eslint` or `mypy` is refused at load with a `LoopConfigError` naming the file, the entry, and the replacement to write; a one-word command Studio never shipped (`pylint`, say) is taken as written. The setup wizard writes commands too, pinned by a test that loads its own output back through the loader. Closes #131.
- Agents building and reviewing code are told to find code with a code index or symbol search before grepping or opening files blind — and, having found it, to open the file at the returned `file:line` and read it there. An index summary or an inlined excerpt is never a substitute for the file, however sufficient the tool claims it is. Applies to the `/forge` writer and editor prompts and to `/spec`'s discovery pass. Tool-neutral: it names no product, so a repo with no index loses nothing.
- `check-install` now also names slash commands that an older Studio shipped and that are still sitting on disk with nothing recording Studio wrote them. The prune can only remove what the manifest remembers, so a command renamed before manifest tracking existed was invisible in both directions — it stayed on disk and the status said everything was fine. These are reported, never deleted, and they count against "up to date". Closes #95.
- CI runs the workflow shell tests (`node --test .claude/workflows/tests/workflow-shells.test.mjs`), so `implementation-loop.js` is guarded on every push. It had a test suite that nothing ran.
- A deadline on the wait for evidence: approving a spec that promised evidence now records when you expect to have it, and a sixth rule in `studio/tests/test_spec_verification.py` turns the suite red once that date passes (built to the approved spec at `specs/verification-due-date.md`). The convention has always let a spec sit at `approved` holding a blank evidence file — that blank file is the pre-registration, the headings committed before anyone knows how it turned out — but it never said for how long, and the answer was forever: the older rules refuse only a spec that *claims* to be done, so a feature could be built, merged and in daily use while its spec quietly stayed `approved` with nothing recorded. The convention's own spec did exactly that for five days, and it was caught because someone happened to ask. `/spec` now writes `verification_due` at approval, 30 days out, in the same step that creates the empty evidence file, and the rule reads that field from the leading `---` block only — a spec quoting it in its prose has not set one. **Two honest exits when it fires:** fill the evidence file in and flip the spec to `shipped`, or move the date. Moving it is allowed and sometimes correct; the point is that it becomes a visible edit somebody can question rather than silence nobody notices. **Named rather than hidden:** CI runs on `push: main`, so a passing deadline can red the tree with no commit involved. A deadline that does not fire on its own is not a deadline
- A `/studio-setup` step that writes the `/forge` gate commands into `.studio/implementation_loop.toml`, where you can read and edit them (built to the approved spec at `specs/stack-aware-forge-gates.md`; the second half of the stack-aware gates below). Detection now decides what `/forge` runs, which is an improvement you cannot see: the commands live in a lookup table inside Studio, and the first sign of a wrong guess is a unit failing on a command you never chose. The step asks no questions and works nothing out for itself — it calls the same `resolve_profile` the loop resolves its gate with and prints the answer to a file, so what you read and what runs cannot drift apart. **It never overwrites a file you already have:** the hand-written override in a repo Studio cannot identify is the only thing keeping `/forge` working there, and eating it would break the exact repo this feature is meant to help. **It writes nothing when detection has no answer:** if Studio recognises nothing at your repo root, or two stacks at once, you get the same refusal `/forge` would print — naming the file and the three lines to write by hand — and no file appears, because a commented-out placeholder would change no behaviour and repeat a message that already says where to write and what. **Re-run `/studio-setup` after updating:** `CURRENT_SETUP_VERSION` goes to 5, so every installed repo reports one pending step until you do. That is the point of the step, and there is deliberately no migration to paper over it
- `shipped_impact` and `shipped_changed` in a spec's frontmatter, and a fifth rule in `studio/tests/test_spec_verification.py` that refuses a `shipped` claim without them (built to the approved spec at `specs/retire-volunteer-metrics.md`). This is where outcome capture moves once the volunteer channels are gone: the moment you know what a feature changed is the moment you flip its spec to `shipped`, and that is a file you already have open. `shipped_impact` is exactly one of `none`, `minor`, or `major` — `none` is a real answer, since a feature that shipped and changed nothing downstream is still worth recording — and `shipped_changed` is one line of plain words on what actually changed. Both stay blank at `draft` and `approved`, because you don't know the answer yet and demanding it early is how you get an invented one. Unlike the evidence rules beside it, rule 5 is **not** limited to specs that promised a `## Verification` section: every feature that shipped changed something, prompt-shaped or not. The two honest exits are the ones rules 3 and 4 already offer — fill the lines in, or set the spec back to `status: approved` and stop claiming it shipped. All ten already-shipped specs are backfilled, each line written from that spec's own In Plain Language section rather than from the fact that it landed. **The gate guarantees a line exists, not that it is true:** ten specs backfilled with "it shipped" would pass and say nothing, and no test can close that. Frontmatter is now read in exactly one place, `stats.parse_frontmatter` — a pure string-in/dict-out reader of the leading `---` block only, so prose discussing a status still cannot declare one — shared by the gate and (next) the dashboard, so the two can never disagree about what a spec says
- `/forge --work-dir <path>` — build a unit in a git worktree instead of wherever the shell happens to be standing (built to the approved spec at `specs/forge-work-dir.md`). The loop hands its git commands to agents as *text in a prompt*, so they have always run in the checkout you invoked `/forge` from, on whatever branch it had open: commits landing on the wrong branch, and a `git reset --hard` from there able to move the main checkout, since worktrees share one object store. Until now the way around that was a private script that rewrote a copy of the loop before every run; it's deleted. Both agent prompts now open with a `cd` into the named directory and an instruction to keep everything there, and every git command inside them renders as `git -C "<path>"`. **The `cd` is the mechanism; the pinned git is only a backstop** — the test command, the static check and the mutation run are not git commands, so `git -C` never reaches them, and pinning git alone would have been worse than doing nothing: the agent would commit to the correct branch and then report green tests describing a different tree. **The path is validated before the loop starts.** `/forge` resolves and checks it before a single agent spawns and stops the run naming which of four reasons it hit — `missing`, `not-a-worktree`, `different-repo` (a worktree of some other repository), or `unquotable` (a path holding a character outside the accepted set). **That last check is an allowlist, not a blocklist:** letters, digits, and `/ . _ - ~` or a space are accepted, everything else is refused, so a character nobody sat down and thought about is refused by default instead of waved through. Enumerating the dangerous ones is a game you lose quietly — two independent reviews each found a fresh way out of that quoting in the handful of lines that render it. The known-dangerous characters are still written down, but only to explain a refusal, never to decide one: a refusal points a caret at each offending character, gives the reason for the ones it recognises, states what is accepted and tells you to rename the directory. The accepted price is that a legitimate path holding a `+`, a `(`, an `&` or an accent is refused too. Checking first is the point: a typo'd path costs nothing instead of failing an hour in with both agents already run. **The honest limit, carried everywhere this is documented:** it reduces the blast radius of a run pointed at the wrong directory; it cannot make that impossible. Every one of these instructions is prompt text an agent may ignore, and the check happens once, at the start, while the agents work for an hour — a test can prove the prompt *says* `cd`, only a live run shows the agent did it, which is what `specs/forge-work-dir-eval-results.md` is for. With no `--work-dir` the key is absent, the `cd` lines aren't rendered and git stays bare, so every existing run is byte-identical
- `/handoff` — save the thread in flight to a durable note so a `/clear` stops being lossy. A long session ends one of two ways: you clear it and lose the thread, or you let an auto-summary carry it and resume from something vague. The note records **state, not history**: what is done *and verified* with its evidence, what is half-built and exactly where, the single next action specific enough to start cold, the decisions already made so they aren't re-litigated, what it's blocked on and on whom, and the landmines that would cost real time to rediscover. Two modes only — `/handoff [note]` saves (overwriting; the note is a snapshot of now, not a log) and then says plainly that clearing is safe, and `/handoff <slug>` resumes. The load-bearing rule is that **a save verifies reality before writing it down** — `git status`, `git branch -vv`, `gh pr list`, and reading the files it claims to have changed — because a note recording what was *believed* is worse than no note at all: it sends the next session confidently in the wrong direction. Resuming re-verifies for the same reason, since branches and PRs move while a thread is parked. The note goes wherever the repo already keeps durable records (the docs tree or vault its `CLAUDE.md` names), falling back to `.studio/threads/<slug>.md` in a consuming repo and `threads/<slug>.md` in the Studio source repo, and it matches that repo's existing note conventions. Deleting the note is how a thread closes. All markdown, no Python: the command is read by the assistant, like `/smoke` and `/unstale`
- Pre-committed verification for **prompt-shaped** features (built to the approved spec at `specs/prompt-feature-verification.md`; borrowed from [obra/superpowers](https://github.com/obra/superpowers), see `studio/docs/SUPERPOWERS_COMPARISON.md`). Some features live in an agent's prompt, where no failing test can tell you they broke — so "it works" has always rested on whoever last read the output. `/spec` now asks for a `## Verification` section on those features: the pass criterion written as an *iff* **before the build**, while disagreeing with it is still cheap; the baseline the old behavior gives you; and where the evidence goes. Approving such a spec creates a `<slug>-eval-results.md` sibling from a skeleton, with its headings — including "What this doesn't prove" — written before any data exists, so a missing answer is a visible hole rather than an omission nobody notices. A spec's `status` gains a third value: `draft → approved → shipped`, where `shipped` is the claim that the feature is verified, and `studio/tests/test_spec_verification.py` makes that claim cost evidence. Four evidence rules as this feature shipped (a fifth, on outcome capture rather than evidence, and a sixth, putting a deadline on the wait for evidence, join them further up this list): an unknown status is rejected (a typo would otherwise disable the rest forever while CI stayed green); a spec promising evidence at `approved` or `shipped` must have its results file; a `shipped` spec's results file must have no placeholders left; and every heading that file was born with must still be there at `shipped`, each carrying at least one line the reporter wrote themselves. Specs that promise no evidence are untouched, which is why the existing ones stay green. The judgment test is in the template itself: *could a failing pytest tell us this broke?* If yes, delete the section — the tests are the criterion and this would be theatre. The gap the first three left — a section quietly cut, or a placeholder cleared with nothing written under it, both reached green with nothing reported — is what the fourth closes: "themselves" means a line `/spec`'s skeleton did not print, so the file's own guidance can no longer stand in for a report. What remains is filler rather than absence: "N/A" under every heading still passes, which the spec records as undetectable in principle
- An escalation channel for a blocked writer in the `/forge` loop (built to the approved spec at `specs/writer-escalation-channel.md`). Until now the writer's only way to report back was a record it had to fill in completely, including the ID of a commit where the tests pass. That works when the writer succeeds and falls apart when it gets genuinely stuck: there is no such commit, so it could either invent a value and pretend it finished, or return nothing valid at all — in which case the run aborted with `writer_failed` and told you nothing about why. The handoff now carries one optional `stuck` field for the blocker, and the writer's instructions say plainly that stopping is allowed and faking a finish is not, with four observable triggers to escalate on (reading file after file without getting closer to a change you can make; needing to change what the unit means to get green; a dependency or interface that doesn't exist or contradicts the instructions; being about to weaken a test). An escalating writer commits whatever partial work it has as `writer(stuck): <unit_id>` — deliberately `--allow-empty`, because the likeliest blocker leaves a clean tree and a plain commit would silently create nothing — so the dead end is a commit you can read, and `git log --grep='^writer(stuck):'` is the tally. The escalation is announced in the transcript the moment it arrives, and `/forge` leads its report with it. No control-flow change: an escalation fails the existing entry gate through the existing mechanics (`mvi_claimed=false`, red tests) and takes the existing deliver-flagged path, so a green unit that merely files an advisory note still gets its editor pass. That entry gate is now a named `passesEntryGate` function with tests, which pins the behavior it has always had — including that an advisory note never costs a green unit its editor pass
- Per-criterion grading in the `/forge` writer/editor loop, fed by an approved spec (built to the approved spec at `specs/unit-acceptance-criteria.md`). Until now the editor's one binding verdict — *if we stopped here, could someone use this?* — was judged against the unit's **title**, a single line of prose. A unit can now carry `acceptance_criteria`: checkable statements of what "done" means. The writer sees them as its definition of done, and the editor grades each one separately — `pass`, `fail`, or `unverifiable`, each with the evidence it actually checked (a test and its result, a file:line, a command run) — returned as `criteria_verdicts` in its handoff and in the workflow's payload, with any criterion that didn't pass named in the run log. `unverifiable` keeps the editor honest: it reads a diff and runs the unit's tests, with no browser and no Play mode, so it is never forced to invent a grade. The MVI question survives alongside the criteria rather than being replaced by them: the unit passes only if it is usable as a complete interaction **and** every criterion passes. A failing criterion ships the unit flagged; nothing reverts (revert is for broken green, not unmet scope) and there is no retry. The gate reads the grades itself instead of trusting the editor's one MVI boolean to reflect them: every criterion has to be matched, by its own text, to a passing grade that carries evidence. So an editor that fails a criterion while still claiming the unit is usable, grades the same easy criterion three times, or passes one with the evidence field left blank, cannot ship unflagged. A run with no criteria is unchanged: the writer's prompt is byte-identical to before and the editor judges against the title. Criteria reach a run through a new pointer, `/forge --spec <slug-or-path> --unit <unit_id>`: `/spec`'s Build Plan is now a contract rather than a summary — each unit gets a snake_case `unit_id` and three to six checkable criteria as `- [ ]` checkboxes — and `/forge` resolves that spec (`specs/<slug>.md` in the Studio repo, `.studio/specs/<slug>.md` in a consuming one, the same repo-shape signal it already uses to find its own loop config), copies the named unit's criteria out verbatim, and prints them in the plan echo so a drifted or invented criterion is visible before a line is written (`--plan` makes that check free). A spec that can't produce criteria for the named unit **stops the run before the loop**, naming which reason it hit (missing file, no Build Plan, unknown or ambiguous unit, empty criteria list), the unit ids it did find, and the two ways forward — add criteria to the spec, or re-run without `--spec`. A typo'd pointer must not silently downgrade to an ungraded run that still looks graded. A `status: draft` spec is the one middle case: it pauses as a P1 decision instead of stopping, because only an approved spec is the source of truth but mid-flow drafts are too common for a hard stop. Without `--spec` nothing changes except one line in the echo, naming how many specs are available to grade against — silent in a repo with none. All markdown: no new command, no parser, no config knob. A Build Plan is authored prose that is deliberately richer than code, so a grammar in front of it would crash on every authoring liberty; the reading agent handles it, and the mechanical part (a criterion that isn't matched to a passing, evidenced grade ships the unit flagged) stays where it already is
- Contrarian evidence gate + independent finding verifier (borrowed from [garrytan/gstack](https://github.com/garrytan/gstack); see `studio/docs/GSTACK_COMPARISON.md` for the study + roadmap). The contrarian's finding discipline gains **quote-to-promote + confidence bands** in `CONTRARIAN_MANDATE`: every flaw must quote the exact thing it critiques or be marked `(unverified)` and demoted, and each finding carries a confidence that sets how loudly it's raised. Findings are now machine-readable — a canonical `FINDING` blockquote (`findings.py`, sibling of `decision_points.py`) parsed into `findings.json`. On top of that, an **independent verifier** (`verifier.py` + `.claude/workflows/finding-verifier.js`): a fresh agent re-checks each Medium-confidence finding from ONLY its quote — never the contrarian's reasoning (the anti-anchoring firewall) — and writes the adjusted confidence back (confirmed → promote, unconfirmed → demote). Built to the approved spec at `specs/contrarian-finding-verifier.md` via `/spec` → `/forge`; the per-finding verifications run concurrently via the Workflow's `parallel()`
- Design-phase critique guide (`design_mandate.py`, gstack R6+R7). `DESIGN_CRITIQUE_GUIDE` injects a game-adapted **AI-slop blacklist**, a "would a designer be embarrassed to ship this?" self-gate, an anti-convergence directive, and the **Goodwill Reservoir** UX score (start at 70, dock for player-hostile choices, credit for respectful ones, report the ledger by line) — into **design-phase** instructions only (`run_phase.build_instruction_doc`), absent from market/tech/studio and `--mode questions`
- Delta-based trend alerts in `stats` (gstack R4). `stats.detect_trend_alerts` adds a "Trend Alerts" block: run-over-run regressions (human rating falling, tokens/cost per run rising) that persist across **2+ consecutive runs** by ≥5% relative — alert on the change, not an absolute, and never on a single-run blip. `--json` gains a `trend_alerts` key
- Doc-parity tests (`tests/test_doc_parity.py`, gstack R2 reframed). The `/spec` debate **rejected** gstack's doc-*codegen* for Studio — the reference docs are intentionally richer than the argparse source, so generating would delete authored prose — and shipped **parity assertions** instead: API.md's command table must match `build_parser`'s subcommands (both ways), and every `ScopeConfig`/`LoopConfig` field must be documented, so a new command or config field can't ship undocumented. Spec at `specs/doc-parity-tests.md`
- Reviewer Concerns in the `/forge` writer/editor loop (gstack). When the editor spots a real problem it can't safely fix this pass (would break green, hits a `load_bearing` item, or is out of the unit's scope), it records it in `unresolved_concerns` + a `reviewer-concerns.md` artifact instead of losing it on the revert — the loop stays one-way but the second agent's most valuable output survives. Plus a **lone-critical override** in the studio integrator's synthesis (a single serious contrarian finding is never buried for lack of consensus) and **named failure-mode anchors** in the decision protocol (a past regression cited in the prompt where it fires)
- Optional model override for the `/forge` writer + editor agents: `implementation-loop.js` takes a `model` arg (e.g. `fable`/`sonnet`/`opus`), inheriting the session model when unset
- Opt-in source fast-forward for `/studio-update` (built to the approved spec at `specs/pull-source-opt-in.md` via `/spec` → `/forge`). Kills a recurring friction for anyone who develops Studio in one repo and uses it from others: you merge a PR (the remote moves ahead) but never `git pull` the local source checkout every consumer reads from, so each `/studio-update` correctly reinstalls from `origin/main` and nags you to pull your source by hand — forever. Now you can opt in and have `update` fast-forward the source *for* you: set `[update] auto_pull_source = true` once in the **source** repo's `.studio/update.toml` (covers every consumer on that machine, since they all resolve the same source), or pass `--pull-source` for a one-off. The pull is strictly safe — **fast-forward only**, and only when the source is clean, on its default branch, and simply behind origin; a dirty/diverged/detached/feature-branch source (or any non-ff) changes nothing and falls back to today's reinstall-from-origin + manual-pull hint. Never a merge, force, or rebase. This deliberately reverses the earlier "never mutate your source" default (source-staleness Key Decision #5), now behind the opt-in and the ff-only envelope. New `_source_auto_pull_enabled` + `SourcePull` + `_fast_forward_source` in `install.py`, a `pull_source` param on `update_studio`, the `--pull-source` flag on the `update` CLI, and `tests/test_pull_source.py`. The `HEAD == default branch` precondition is the load-bearing guard (source staleness is measured on the local branch regardless of where HEAD sits). `check-install` stays read-only.
- Proactive update-availability nudge for consuming repos (built to the approved spec at `specs/update-availability-nudge.md` via `/spec` → `/forge`). You no longer have to remember to check whether your installed Studio is behind: `init`/`update` install a per-user Claude Code **SessionStart hook** (in `.claude/settings.local.json`) that runs a new lightweight `check-updates` command once per session. It compares the commit you installed from against the source's current `origin/main` HEAD and, if they differ, surfaces a one-line nudge to run `/studio-update`; silent when current. The check is cheap and quiet: a bounded, best-effort `git fetch` at most once per 24h (cached in `.studio/update-check.json`), near-instant on repeat sessions, offline-safe, never mutates files, and always exits 0 so it can't break a session. It nudges once per new upstream commit. Opt out with `init`/`update` `--no-hook` or a durable empty `.studio/update-check.off`. The hook uses the absolute `sys.executable` (so it survives a `python`-only-`python3` environment) and lives in the gitignored `settings.local.json` because it's machine-local — it only fires on the box that ran `studio init`, and a teammate who merely cloned the repo gets a safe no-op. New `compute_update_check` + `UpdateCheck` + `_install_sessionstart_hook` in `install.py`; `check-updates` subcommand in `run_phase.py`; `tests/test_update_check.py` + `tests/test_hook_install.py`
- Source-staleness detection for `check-install` / `update` (built to the approved spec at `specs/update-staleness-detection.md` via `/spec` → `/forge`). The updater used to measure "up to date" against your *local* Studio source checkout — reading its committed `main`, never fetching, and comparing file contents — so if that checkout was behind its remote (unpulled), everything looked byte-identical and it confidently reported "up to date" against a stale mirror (the recurring pain in consumer repos). Now a bounded, best-effort `git fetch` of the source's default-branch remote (short timeout, `--no-fetch` opt-out, offline-safe fallback to cached refs) checks whether local `main` is behind `origin/main`. When it is: `check-install` suppresses the "up to date" verdict, exits non-zero, compares against `origin/main`, and prints the exact `git -C <source> pull` command; `update` refuses to no-op and reinstalls from `origin/main` instead. It never mutates your source repo (no auto-pull). Every can't-tell case — offline, no remote, detached HEAD, not a git repo, or local merely *ahead* of origin — falls through to today's behavior, so it only ever adds a block, never a false one. New helper `_source_staleness` + `SourceStaleness` in `install.py`, computed in each of `check_studio` / `update_studio`'s own scope (a regression test, `test_update_stale_source_reinstalls_from_origin`, permanently guards against routing it through the delegated `check_studio`, which would silently disable it on `/studio-update`).
- `/spec` slash command: maps a feature's architecture into an approved, source-of-truth spec document before you build it. It reuses the existing debate machinery — a single advocate/contrarian `tech`-phase pass, scope-paced to be discovery-forward: the alignment scope folds in the Open-Questions Pre-Flight to surface and answer the architectural unknowns (pausing on P0 blockers), then the depth scope pressure-tests and finalizes the design. It then synthesizes one document written for two readers at once — a plain-language summary a non-engineer follows, plus build-ready technical detail (components, data flow, interfaces, data model), a required Mermaid diagram, the key decisions and cut scope from the debate, open risks, and a build plan of MVI units that bridges to `/forge`. A run ends by pushing the spec as a pull request at `status: draft` — not by leaving a file in the working tree. That PR is the review and merging it is the approval, after which the status flips to `approved`. The doc is tracked under `specs/` (or `.studio/specs/` in a consuming repo), linked to its ticket via frontmatter. Args: feature text, `--ticket`, `--id`, `--max-iterations` (default 2), `--plan`. No new Python — the command markdown drives it. Ships on cross-repo install
- Coding principle 9, "Spec Before Build": a non-trivial feature gets an approved architecture spec (via `/spec`) before implementation, tracked with its ticket. Building without one decides the architecture implicitly, commit by commit, with no whole-picture view and no record of why; a spec front-loads the unknowns while they're cheap to change and gives one source of truth to build against. Explicitly scoped to features and meaningful changes, not one-line fixes. Reaches installing repos through the same `CLAUDE.md` sentinel injection that carries the other principles
- Coding principle 8, "Talk to Humans": how the agent speaks in the live conversation, alongside the existing rules for docs (§6) and code (§7). Updates and decision-flags are written for a reader who hasn't opened the files, docs, or notes the agent just produced — lead with what changed and why it matters, don't drop bare internal handles (file names, config keys, PR/ticket IDs) as if they explain themselves, and when asking for a call, give enough context plus a recommendation to answer without digging. Reaches installing repos through the same `CLAUDE.md` sentinel injection that carries the other principles
- `/smoke` slash command: stands up a live, running version of whatever the repo builds so you can hand-test it (web app on a URL, game in Play mode, service on a port, CLI). Distinct from tests-green: a smoke means the thing actually runs and a person can use it. The command detects a profile, preps/builds, launches in the background, polls readiness, then hands off the entry point plus a golden-path checklist and tears down on request. Stack-agnostic self-detection, or an optional per-repo `.studio/smoke.toml` (`[smoke]` table) pins the exact setup/build/launch, readiness check, and golden path; Unity projects stand up via MCP Play mode. Ships on cross-repo install; setup wizard gains a `smoke_config` step (`CURRENT_SETUP_VERSION` 4) that authors the file via `suggest_smoke_from_stack`
- Session analytics, first slice (built via the `/forge` writer/editor loop). `finalize` now auto-writes a judgment-free `session.json` health record into each run dir: convergence (iterations + rejections), decision profile (surfaced/answered/assumed by priority, incl. the assumed-P0 count), clarity delta, cost per settled decision + scope spend, and an editor-liveness word-count block. No human rating, additive and soft-fail (`session.py` builds it, `run_phase._write_session_record` wires it). ### Fixed
- `/studio-setup` can now actually apply an answer. Every step in the command's instructions hands `setup --answers` a JSON object on the command line — `--answers '{"cleanup": {...}}'` — but the flag was defined as a path and the value was passed straight to `open()`, so each of those documented commands died on `No such file or directory: '{...}'` before reaching any configuration code. The flag now takes either: a value starting with `{` is parsed as JSON, anything else is read from disk as before. The two can't be confused, since no filename starts with `{`, and no step has to write a temp file just to answer a question the wizard already knows the answer to
- `/forge` now reads its quality-gate commands from the repository it is building in, instead of running `pytest`, `ruff` and `mutmut` everywhere (built to the approved spec at `specs/stack-aware-forge-gates.md`). Studio is installed in ten repos; three are Node, one is Rust, one is Unity, and in each of them every unit failed the gate for a reason that had nothing to do with the work — the gate was asking the wrong question. The loop now looks at the marker files at your repo root: `pyproject.toml`, `setup.py`, `requirements.txt` or a root `conftest.py` keeps the Python commands; a `package.json` **that declares a `test` script** gets `npm test`, plus `eslint` when the repo shows a sign of having it. When it recognises nothing, or two stacks at once, it **refuses to start** and prints the repo it looked in, what it found, and the exact three lines to write in `.studio/implementation_loop.toml` — five repos land here, so that message is the feature's main interface, not an edge case. There is deliberately **no escape hatch**: the only value that could satisfy a "skip the gate" knob is a command that does nothing, which reopens the hole the refusal closes. **The real fix is the deletion**, not the detection: the shipped `config/implementation_loop.toml` hard-set all four gate keys, nine of the ten repos have no config file of their own and so resolve to it, and while it existed it won over anything detection computed. Its `[gate]` table is gone — the file itself stays in the install list, because there is no prune for `.studio/source/` and removing it would strand the old copy, `[gate]` intact, in all ten repos forever. Two smaller things ride along. **A `[gate]` table in your own file now merges over what was detected**, so a Unity repo naming only its test wrapper stops inheriting another language's linter (the same bug, one level down). And **no ranking of markers**: a Rust game whose `package.json` is only CI tooling would otherwise be handed `npm test`, which passes while testing none of the game — a wrong-reason *pass*, worse than the failure being fixed. Rust is recognised precisely so that repo is refused rather than answered. The repo that reported the problem, Orkid Garden, is **not** auto-fixed: its Unity project sits in a subdirectory so nothing at its root identifies it, and Unity has no honest test command to ship anyway — its hand-written override remains the answer, and there is a test holding this change to not disturbing it
- A finished run now leaves its contrarian findings as `findings.json`, so the independent verifier has something to read. Every contrarian prompt has been asking agents to emit `FINDING` blocks since the verifier shipped, and `findings.py` has been parsing them in tests — but no production code path ever called the extractor, so the blocks sat unparsed in the run's markdown and the verifier waited on a file nothing created. `finalize` now extracts them and writes the file, a few lines from where it already does the same for decisions. Two rules, both deliberate: a run whose contrarian found nothing gets **no file at all** (a missing `findings.json` is already the verifier's "nothing to verify" case, and an empty one would be a lie about a run that was never checked), and an **existing `findings.json` is left completely alone** rather than merged. That asymmetry with the decisions path next to it is the point: the verifier round-trips through this same file, writing adjusted confidences back into it, so re-extracting over one would silently destroy every verdict it recorded
- The update-check hook survives an `update` instead of being deleted by it (#120), so consuming repos will now actually be told when their installed Studio is behind. The nudge shipped in a state where it could only fire in a repo nobody ever updated: `update` installed the hook up front, then re-installed Studio with `install_hook=False` — which `install_studio` reads not as "leave it alone" but as "remove it", its documented behavior for that flag. So every update that did any real work deleted the hook it had written milliseconds earlier. That is why `_Cerebro` drifted 185 commits behind with the anti-drift feature installed. The fix is one argument: the re-install is handed the caller's real intent, so the second pass agrees with the first instead of contradicting it, and `--no-hook` and the `.studio/update-check.off` sentinel keep working exactly as before. **Why the tests stayed green through all of it:** an update against an already-current target returns at the up-to-date short-circuit, before the re-install, so the hook survives and the existing coverage passed on the broken code. The new regression tests in `tests/test_hook_install.py` make the target genuinely out of date first, and assert the update did real work before checking for the hook — that ordering is the part that binds
- The `/forge` writer's mutation check no longer measures nothing when mutmut is absent. The fallback told the writer to "break 2-3 critical **assertions**, confirm the tests FAIL, then restore" — but breaking an assertion fails its own test by construction, so it proves only that the test runs, never that it would notice a real bug. `AI_TDD_METHODOLOGY.md` has always said to break the production **code** the assertions guard; the prompt has disagreed with the methodology since the loop shipped, and the whole no-mutmut arm of the gate was close to tautological. It now says to change 2-3 things in the production code the tests cover — flip a comparison, drop a guard clause, return a constant — and spells out why mutating an assertion instead is worthless, since that is the mistake it is correcting. The handoff field `mutation_check.assertions_broken` is renamed to `mutations_introduced` for the same reason: a field name is an instruction, and this one was quietly teaching the wrong check. Found by the [obra/superpowers](https://github.com/obra/superpowers) study (`studio/docs/SUPERPOWERS_COMPARISON.md`), which reached the opposite conclusion on the mechanism that surfaced it — the "I watched the test fail" handoff field was **rejected**, because Studio's mutation rule already proves the stronger property with a real tool; these two one-liners were the genuinely useful thing it turned up
- The `/forge` editor now treats a noisy passing suite as a finding. "Test output pristine — new warnings are a finding" appeared nowhere in Studio, so a unit whose diff introduced a deprecation warning or stray output shipped as clean, and the warning became someone else's problem several units later. The editor's hard bounds now say green is not enough, and route anything it can't fix in the pass to the existing Reviewer Concerns channel rather than letting it evaporate on a revert. **The honest limit on both of these:** they are prompt text, so the tests can only prove the instruction says the right thing — the fixture pinning the writer and editor prompts was regenerated deliberately, and its diff carries these two changes and nothing else. Whether the agent then does it is what a live run shows
- Studio recognizes its own source repo (built to the approved spec at `specs/source-repo-detection.md`). Running `python studio/run_phase.py <cmd>` from the repo root — the invocation `CLAUDE.md` documents — made Studio classify **its own repo as a consuming repo**, because the source repo carries a bare `.studio/` (for `update.toml` and `usage.log`) with no `VERSION`, which is exactly Studio's signature for an already-scaffolded consumer. Since 2026-07-08 that meant run artifacts landing in `<repo>/.studio/output/` instead of `<repo>/studio/output/`, and `_scaffold_external_repo` writing a stray `docs/studio-bridge.md` into the source tree — a welcome note addressed to itself. The fix is one branch in `get_artifact_root()`, above the `.studio/VERSION` walk-up: a `studio_root` that is not an installed snapshot, with cwd under its parent, is the source repo. It restores an invariant the rest of the module already documented — `get_output_root`, `get_knowledge_log_path`, `_project_name` and `get_outcomes_ledger_path` all already branched on `artifact_root == studio_root` meaning "this is the source repo", and `impl_loop.py` resolved it this way with no cwd test at all; `run_phase` was the outlier. Nineteen stranded run directories were migrated back into `studio/output/`, so `stats` reports 8 runs where it saw 3; two of them turned out to be a single run split across both locations, and two others were different runs sharing a `unit_id` whose identically-named handoffs would have silently overwritten each other. **One behavior change worth knowing about:** moving the artifact root also moved where a source-repo run looks for `integrations.toml`, so a config at the new path became live for the first time — enough to start posting Slack digests on finalize as a side effect of a path fix. Digests are switched off there deliberately, and a test now pins which path the resolution lands on. That file is gitignored, so it is machine-local: a fresh clone has no `integrations.toml` at all, which resolves to no enabled target rather than a default-on.
- `/handoff` reached no project, and renamed commands never left one. Two halves of the same gap: the installer copies commands from a hand-maintained list in `install.py`, and `/handoff` was added to `.claude/commands/` without being added to that list — so `init`/`update` never shipped it anywhere, and `check-install` couldn't report it missing, because "missing" is measured against the list too. Same shape as the omitted `integrations` subpackage below. The other half is the reverse: the list is also what the manifest is built from, so when `/studio-implement` was renamed to `/forge`, the old file dropped out of the manifest and simply stayed on disk in every installed project — two commands for one job, the stale one holding the pre-rename behavior, and `check-install` calling it up to date. `update` now DELETES the commands and workflows Studio has stopped shipping (reported as `Removed:`, previewed by `check-install` as `Retired`), and a leftover counts against "up to date" so the update can't short-circuit past it. Only files the manifest records — ones a past install wrote — are ever deleted, so a command you wrote by hand in your own project is untouchable; one you *edited* goes through the existing clobber guard, blocking until `--force`. Retired files under `.studio/source/` are deliberately left alone. Guarding the recurrence rather than just this instance: `tests/test_install.py::TestCommandRegistration` fails if any command or workflow in the repo isn't registered with the installer (and if any registered name has no file), the sibling of the existing snapshot-import guard for source modules
- `check-install`/`update` now read Studio source from the **default branch** (`main`), not whatever branch the upstream source checkout happens to be parked on (or its uncommitted edits). Consuming repos resolve their upstream to a local working tree and read its files directly, so a source repo left on a feature branch used to leak that work-in-progress into other projects' update checks — they compared against the branch, and once they'd copied it, reported a false "up to date." The check now materializes the default branch's committed tree in a throwaway worktree, reads from there, and notes which branch it bypassed; `update` copies from `main` while still recording the durable upstream path in `VERSION`. Falls back to reading the working tree as-is when the source isn't a git repo or is already on `main` and clean
- `update` now refreshes the coding-principles block in a project's `CLAUDE.md`. That block is injected once at install time between sentinel markers and was never a manifest file, so a checksum-only `check-install` never noticed when Studio's principles moved ahead (e.g. the new "Talk to Humans" principle) and reported "up to date" while the block sat behind. `check-install` now compares the installed block against the current template and flags it; `update` re-injects it in place, leaving the rest of `CLAUDE.md` — your own project notes above and below the markers — untouched

Also retargeted the `CROSS_REPO_CHECK_MVI` doc, which described a never-shipped `studio check` command with output it doesn't print, to the actual `check-install` behavior
- `update` no longer silently overwrites your local edits to slash commands or workflows. It already protected the Studio source files; now it also tracks the installed `.claude/commands/*` and `.claude/workflows/*`, so `check-install` flags an edit you've made to one of them and `update` stops before overwriting it (pass `--force` to overwrite anyway)
